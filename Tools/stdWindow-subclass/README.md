# stdWindow subclass bridge

The embedded bridge adapts the Windows six-argument `SUBCLASSPROC` ABI to
`stdICallable.Run` with four boxed message arguments. `dwRefData` holds the typed
interface pointer; `uIdSubclass` distinguishes wrappers sharing the same HWND.
The low dwRefData bit is the per-registration IDE-safety opt-out flag. It is
cleared before all COM calls, including AddRef and Release. Other bits hold the
pointer unchanged. This allows guarded and unguarded wrappers to share one thunk.
The typed vtable includes IUnknown/IDispatch followed by Run at slot 7. The bridge
uses AddRef/Release around the complete COM call, and its result is always a
pointer-sized integer produced by stdWindow's internal interface implementation.
The user callback itself runs through its typed RunEx method.
stdWindow creates a normal VBA-owned argument array for that user call; the
callable can safely resize or retain it independently of the native stack.

Each invocation builds its own SAFEARRAY descriptor, argument VARIANTs and return
VARIANT on the stack. A shared active-call counter prevents freeing the thunk
while a callback frame is still executing. The x64 bridge reserves 216 bytes
(including shadow space), keeps 16-byte call-site alignment, and registers a
matching Windows unwind record. x86 uses stdcall stack cleanup and 16-byte
VARIANTs; x64 uses 24-byte VARIANTs. Code is RX, while the counter is in a separate
RW page. Both thunks forward through DefSubclassProc if the COM call fails.

Before accessing the VBA interface (even AddRef), the thunk checks EbMode:
Run=1 dispatches; Break=2 forwards and preserves the subscription; Design=0 or an
unknown value removes the subclass natively and forwards. WM_NCDESTROY detaches
even in Break mode. The registration counter is native, so this works without
calling a VBA destructor or reading cleared globals. isSubclassed queries the
actual Windows registration, reconciling native detachment on the next VBA call.

The loaded VBE may not export EbMode by name. stdWindow tries that export first,
then discovers the internal function from its Proc/MethCallEngine template.
This follows the technique documented by [The trick's SearchEbMode](https://github.com/thetrik/VbTrickTimer/blob/master/Class/CTrickTimer.cls).
Our resolver uses copied image data instead of overlaying SAFEARRAYs onto live
code. PE headers, architecture, section bounds, the complete masked signature,
target module membership and committed executable memory are checked. Repeated
templates must agree on one target; distinct targets or unknown layouts return
zero and installation fails. No version-specific offset is assumed.
The guarded default refuses an unresolved function; an explicit safety opt-out
does not need a resolved mode pointer and never calls the mode-check branch.

Discovery runs once per predeclared stdWindow lifetime and caches the actual
function pointer. Callbacks make a direct native EbMode call. There is no
VBProject.Mode fallback, retained editor object, symbol/PDB download, or VBOM
permission requirement. stdWindow itself changes no Trust Center settings.
The writable page contains +0 active DWORD and +4 registration DWORD; the x64
callback retains its single unwind record and 216-byte frame.

Changing the x64 prologue requires changing the embedded UNWIND_INFO as well.
The generator checks the expected prologue and available code space.

## Developer commands

```powershell
python -m pip install keystone-engine unicorn pywin32
python -B Tools/stdWindow-subclass/build.py
python -B Tools/stdWindow-subclass/build.py --check
python -B Tools/stdWindow-subclass/test_thunk.py
python -B Tools/stdWindow-subclass/run.py
```

Keystone and Unicorn are developer dependencies only. Importing stdWindow needs
neither package nor a helper VBA module. Sources generated by build.py use CRLF.

The ABI tests emulate both architectures and check boxing, retained interface
references, stack cleanup/alignment, register preservation, return width and the
HRESULT failure path. Additional tests cover EbMode guards,
including Break, Design, unknown modes, failed removal and destruction
while paused, using invalid VBA pointers to detect accidental dereferences.
Emulation does not replace running 32-bit Office.

The Windows runner uses a separate hidden Excel instance and disposable workbook,
adds the existing stdWindow accessibility reference, validates source bytes before
every import, creates a disposable UserForm, and runs tests/stdWindowSubclassTests.bas. It discovers Excel/VBE
versions and existing VBA project access, respects managed AccessVBOM policy, and
restores exact registry values/types (or absence) after temporary changes. Its
dialog monitor dismisses and records dialogs only in the worker's Office process;
a dialog or timeout fails the run. The runner kills only the PID obtained from
that test instance if cleanup is necessary. It does not run the broad legacy
stdWindow suite, which depends on a particular interactive workbook/UserForm.
IDEProbe.bas additionally tests real Design, Stop/Continue, VBE Reset and End.
It also checks modeless dispatch after the starter macro returns with the guard
explicitly disabled. With safety enabled, Design mode detaches even when a
modeless form remains loaded, so callbacks between macros require that opt-out
and explicit Unsubclass before break/reset/End/code edits.
The coordinator uses only the disposable instance's editor controls; its English
Run menu is required for the Stop/Continue and Reset automation. Compile/error
dialogs always fail the run, including those shown during the IDE probes.
The resolver tests invoke the real VBA scanner against mapped synthetic images:
valid/invalid headers, architecture mismatch, ambiguous and agreeing targets,
invalid/non-executable pointers, corrupted signatures and section boundaries.
The runner also saves a disposable macro-enabled workbook, starts a separate
Excel instance with AccessVBOM disabled, verifies project access is denied, and
reruns the window/UserForm/resolver assertions. This negative variant is skipped
if managed policy forces access on. Exact original registry values are restored.
After successful assertions and graceful workbook/Excel closure, the disposable
Python worker exits without running late COM proxy finalizers, which can hang
after denied VBOM calls. The parent still enforces the timeout and owns PID cleanup.

Explicit Unsubclass is still recommended for deterministic resource cleanup.
Do not End/reset/edit code inside an active callback: a guard cannot undo entry
into an already executing VBA frame, nor infer a reset without observing a
non-Run mode. Abrupt reset can orphan the native allocation
until process exit. The guard provides message-time mode protection, not a hook
of the VBE reset routine or complete protection against every IDE action.
